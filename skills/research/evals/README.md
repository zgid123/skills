# Research skill evaluations

Run `python3 scripts/validate_skills.py` from the repository root to check metadata, links, registration paths, evaluation cases, and fixture existence. This validates structure, not research behavior.

The cases in `evals.json` use a closed, explicitly fictional [research packet](fixtures/research-packet.md) and [efficiency fixtures](fixtures/efficiency-catalog.md) so screening, arithmetic, evidence boundaries, and retrieval choices can be checked without unstable live results. Do not present the fixture publications as real sources. The prompts deliberately omit the blacklist to test whether the skill supplies the policy.

The [learning catalog](fixtures/learning-catalog.md), linked [method extract](fixtures/learning-method.md), and [prior learning notes](fixtures/learning-prior-notes.md) add five learning scenarios (11–15): beginner orientation and reading order, detailed mechanism and notation, related-concept follow-up, source-grounded concept mapping, and an abstract-only explanation. Treat these publications as fictional too. Cases intentionally use normal learning requests rather than explicitly forbidding document creation, so an unsolicited manuscript or note-system workflow is observable. Harness writes of answers and transcripts are evaluation artifacts, not user-requested exports.

## Behavioral evaluation

Use the repository's skill-creator workflow. For revisions, snapshot the current skill before editing and compare the revised skill against that snapshot; use a no-skill baseline when evaluating the initial skill. Execute each case and configuration in a fresh isolated session with the same task and fixture access. Keep the baseline isolated from the revised skill and its integration links. Pass the listed entry files and permit linked fixture reads without preloading all supplements: selective retrieval must be observable. Save responses, source-read transcripts, and grades in a sibling research-workspace directory. Grade the `expectations` against the actual outputs and reads, citing evidence; use that array as the assertions when preparing skill-creator metadata.

Generate the human review artifact with skill-creator's `eval-viewer/generate_review.py`. Report structural validation and behavioral evaluation separately. One run per configuration is a smoke comparison, not a reliable estimate of general improvement; cases sharing an agent session are not independent runs. Record unavailable metrics as unavailable, never fabricated timings or token counts.

## Coverage and limits

The five scenarios test blacklist matching and version relationships, abstract-only reading, heterogeneous evidence and novelty, manuscript revision without results, and formatting-only preservation. The expected arithmetic in the comparison case is a 10 percentage-point increase for B and a 10 percentage-point decrease in the observational comparison C; these do not estimate the same causal effect.

Four additional cases in the fictional efficiency fixtures cover three efficiency scenarios: selective reading, focused completion with a formal-review variant, and resuming prior work. They test retrieval of central and conflicting evidence, avoidance of irrelevant supplements and redundant reads, protocol completion, and response to a correction. The focused-completion and formal-review cases receive completed-notes-only entry files; the resume case receives the incoming correction and X. Keep each case’s supplied evidence separate. Do not expose a known correction and then require it to be ignored to satisfy a cutoff.

Assess usefulness, citation support, evidence coverage, unnecessary retrieval, and repeated work alongside available time, token, and tool-call metrics. Count source reads separately from setup and output writes. Compare paired runs on the same case; fewer calls only indicate improvement when evidence support and answer quality are retained. Closed-fixture tasks can show retrieval choices and reuse, but do not measure live-search stopping or real-world retrieval speed. Repeat independent runs before claiming efficiency gains; a single pair per case is a smoke check. Record unavailable metrics as unavailable rather than zero, and do not treat variation across different cases as repeated-run variance.

These fixtures do not verify live search retrieval, publisher metadata resolution, bibliographic service integrations, full-PDF extraction, or document rendering. Test those separately on an actual project before making claims about tool coverage or submission readiness. Human review should also assess usefulness, clarity, and discipline-appropriate reasoning rather than just whether expected phrases appear.

For the learning cases, inspect whether the answer actually teaches the mechanism, defines essential terms, distinguishes illustration from evidence, and gives a purposeful next step. Check each map relationship against the inspected sources; a list of linked titles is insufficient. In the follow-up case, the supplied K supplement supports recall/precision calculations while prior M notes cover unchanged claims, so reopening M is unnecessary. Correct example values are precision 80% → 50% and recall 40% → 50%. For M, the top-result relevance change is +10 percentage points with 15 ms versus 55 ms latency on one synthetic collection; this is distinct from candidate recall or precision. For N, only the abstract's 12% relative latency reduction is known; its actual selection rule and quality preservation are unavailable.

## Standalone installation

Case 10 runs with only Research installed: omit Documents and Data Analyst, perform the requested calculation with an available tool, and deliver the research memo using local guidance. Assert that missing companion skills do not cause failed reads, installation requests, or skipped work. Keep comparison artifacts and review pages outside the reusable skill package; they are not installation prerequisites.
